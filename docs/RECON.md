# RECON.md — repetit.ru, ЛК репетитора

Последняя живая разведка: 2026-09-03, реальный аккаунт, Chrome через CDP `:9335`.
Этот документ хранит **факты площадки**, которые были подтверждены наблюдением.
Текущее поведение воркера описано отдельно в `SPEC.md`.

Историческая разведка включала открытие карточки, формы отклика и одну реальную
отправку. Side-effect-пробы после фиксации результатов удалены из репозитория.
В `scripts/diag/` оставлены только безопасные наблюдательные сценарии `01–03`.
Сырые диагностические дампы пишутся в gitignored `logs/recon/`.

## 1. Платформа

- Личный кабинет `/lk/*` — SPA на React Native Web.
- У значимых элементов встречаются стабильные `data-testid`; для runtime это
  предпочтительнее CSS-классов `r-*`/`css-*`.
- Данные ленты приходят JSON XHR/fetch через `/lk/api/*`.
- Состояние чатов читается через `/api/teacher/chats/*`.
- Отправка сообщения в чате уходит через WebSocket; отдельного XHR POST,
  подтверждающего Send, в разведке не обнаружено.

## 2. URL

| Назначение | URL/path |
|---|---|
| Главная ЛК | `/lk/teacher/home` |
| Лента «Новые заявки» | `/lk/teacher/neworders` |
| Карточка заявки | `/lk/teacher/neworders/{order_id}` |
| Чат по заявке | `/lk/teacher/chatforteacher?orderId={id}&chatTitle={encoded}` |
| Логин-стена | `/lk/loginwithshortcode` |

Прямой `goto` в `chatforteacher` работает. Открывать карточку перед этим не
обязательно.

## 3. Лента: подтверждённый network contract

При загрузке `/lk/teacher/neworders` наблюдалось:

1. `POST /lk/api/teacher/searchOrders`
   - request body формирует сама площадка из настроенного фильтра;
   - response — плоский массив ID заявок;
   - порядок выглядел как новые сверху, но это не считаем формальным API-гарантом.
2. `GET /lk/api/teacher/orders?ids=...`
   - response — массив полных деталей заявок;
   - первый экран давал детали примерно для 21 заявки;
   - дальнейшая глубина связана со скроллом и в текущий MVP не входит.
3. `GET /lk/api/teacher/orders/{id}`
   - вызывается при открытии конкретной карточки.

Runtime не отправляет эти запросы напрямую. Он reload'ит страницу и пассивно
слушает ответы, которые делает сайт.

### Поля детали заявки, используемые проектом

Подтверждены и используются:

- `id`;
- `subject.id`, `subject.name`;
- `purpose`;
- `information`;
- `minPrice`, `maxPrice`;
- `contactName`;
- `area.cityName`;
- `homeMetroName`;
- `lessonPlace`;
- `pupilCategory.name`;
- `orderDate`;
- `subjectAdditions[].name`;
- `subjectDivisions[].name`.

Для online-заявки в живом примере `lessonPlace == 4`. Булевы поля вида
`lessonPlaceRemote` в том же ответе не совпадали с фактическим форматом, поэтому
`Order.is_remote` опирается именно на int-enum `lessonPlace`.

## 4. Важный side effect: viewed

Открытие `/lk/teacher/neworders/{id}` меняет серверное состояние `viewed`.
Обычная загрузка ленты и получение batch-details такого эффекта в разведке не
показали.

Следствие для архитектуры: runtime триажит заявку по batch-details и **не
открывает карточку заявки**. Для первого сообщения он идёт сразу в chat URL.

В feed были обнаружены testid карточек, в том числе:

- `new-orders-list-item-container-{id}`;
- `new-orders-list-item-touchable`;
- `order-list-item-info-subject-name`;

- `order-list-item-info-price`;

Runtime feed сейчас не зависит от DOM этих карточек: источник данных — network
capture. Эти testid полезны для диагностики при изменениях сайта.

Для чата подтверждены:

- `[data-testid="message-composer-input"]`;
- `[data-testid="message-composer-send-button"]`.

## 6. Проверка существующего чата

При открытии chat URL сайт делает (живой факт 2026-09-04):

`GET https://ws.repetit.ru/api/chats/personal?orderId={id}&teacherId={tid}`

- пустой чат (истории нет) — **HTTP 204, тела нет**;
- чат с историей — HTTP 200 (в старом эндпоинте `/lk/api/teacher/chats/order`
  наблюдались `result.lastMessage`, `result.messages`; сам он площадкой больше
  не дёргается, распознавание оставлено в коде на всякий случай).

Это используется в текущем Контуре A как независимый дедуп-гейт **до ввода
текста**:

- если есть `lastMessage` или непустой `messages`, новое первое сообщение не
  отправляется;
- 204 = истории нет, можно отправлять;
- если ответ не пришёл, статус не 200/204 или payload нельзя прочитать,
  Send не выполняется; незнакомая форма ответа трактуется как «история есть»
  (лучше скип, чем дубль);
- отсутствие локальной строки SQLite само по себе не является достаточным
  доказательством, что клиенту ещё не писали.

Это важнее первоначального решения «дедуп только по SQLite».

## 7. Отправка первого сообщения

Живой flow 2026-09-03 подтвердил:

1. прямой переход в `chatforteacher`;
2. появление composer;
3. человеческий ввод текста;
4. клик Send;
5. сообщение появляется в DOM чата;
6. composer очищается;
7. затем интерфейс может предложить «Обменяться контактами».

Так как транспорт Send — WebSocket, runtime подтверждает успех по DOM. После
review инвариант строгий: `sent` только если одновременно найден наш текст и
composer пуст. Если Send был нажат, но оба признака не подтверждены, состояние
`unknown` и повтор запрещён.

## 8. Контакты и платная квота

Площадка явно предупреждала, что передавать контакты в тексте сообщений
запрещено и это может привести к блокировке аккаунта.

«Обменяться контактами» — отдельное действие и отдельная квота. В живой
отправке первое сообщение само по себе эту квоту не списало.

Следствия:

- текст проходит `textguard` до Send;
- кнопка обмена контактами не автоматизируется;
- телефоны, email, ссылки и мессенджеры в тексте запрещены.

## 9. Сессия

При отсутствии сессии `/lk/*` редиректил на `/lk/loginwithshortcode`.
Автологин не исследовался и намеренно не входит в проект: логин выполняет
владелец вручную.

Текущий BrowserManager определяет `AUTH_REQUIRED` по URL логин-стены. Для
рабочего состояния он требует реальную feed URL, а постоянную вкладку воркера
отличает от ручных вкладок fragment-маркером `#repetit-worker`. Fragment не
отправляется HTTP-серверу.

## 10. Что остаётся непроверенным/не гарантируется

- официальный максимальный размер первого сообщения; живые тексты порядка
  нескольких сотен символов принимались;
- формальная гарантия сортировки `searchOrders`;
- поведение и контракт деталей при глубоком скролле дальше первого batch;
- устойчивость testid и API paths к будущим релизам площадки;
- browser E2E текущего review-branch после изменений safety-гейтов.

Поэтому после значимого изменения browser/network flow нужен один контролируемый
canary: `once --dry-run`, затем одна реальная подходящая заявка и проверка, что
повторный цикл не создаёт дубль.
